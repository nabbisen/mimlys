# RFC 005 — Execution worker and sandbox profile

**Status.** Accepted (owner sign-off 2026-10-27; Q-1 … Q-4 of the review taken as recommended)
**Tracks.** Decisions D-10, D-16 and D-06 v2 of the startup review; findings R-06, R-18, C-12, X-07, M-14; threats THR-05, THR-11, THR-12, THR-17, THR-19, THR-32.
**Touches.** `mimlys-exec` (the worker binary, the Wasmtime sandbox, the confinement interface and probe, `run_script` and `run_wasm`), the worker protocol, the data-directory layout (`interpreters/`), the configuration (`[interpreters]`, RFC 010's M2 part), external design §7.4, §12, §13.1, §13.4.

## Summary

Run every piece of generated code in a separate worker process, inside Wasmtime with three independent guards (fuel, epoch deadline, memory limiter), a WASI boundary that sees exactly the workspace and an ephemeral temp directory, no network, no environment and coarse clocks; report every termination with one of eight names; pin the engine and the interpreter builds by exact version and content hash; and put the operating-system confinement of the worker behind one interface with a probe that states, clause by clause, what this machine enforces.

## Motivation

- The drafts described "a WASI sandbox" without saying which guards exist, which fires first, or how the outcome is named (C-12, X-07).
- Generated code must never run in the runtime process: a fault, a leak or an engine flaw must cost one execution, not the task record (D-10, THR-17).
- Interpreter builds are code the user did not write and did not review; they must be pinned and verified, not downloaded at build time or taken from the path (THR-12, M-14).
- The confinement of host tools (M6) and the confinement of the worker share one contract; the probe and the tier must exist before any backend lands so that the status is honest from 0.2 on (D-06 v2, D-07 v2).

## Decision

The normative text is external design §7.4 (execution record and termination), §12 (sandbox profile), §13.1 (worker), §13.2 (contract), §13.4 (probe and tier), §11 (`run_script`, `run_wasm`), and requirements REQ-SBX-001 … REQ-SBX-012, REQ-ARCH-007, REQ-ARCH-008, REQ-CONF-001, REQ-CONF-002, REQ-CONF-003, REQ-CONF-009, REQ-CONF-010, REQ-SEC-006, REQ-SCHED-003, REQ-TEST-008, REQ-TEST-013. In brief:

1. **Engine.** Wasmtime pinned to exactly `50.0.0` (with `wasmtime-wasi` at the same version), core modules targeting wasip1 (D-16), Cranelift only, no component model, no threads, no shared memories. Every engine update is a reviewed change that names the advisories fixed and the features gained (REQ-ARCH-007). Non-deterministic floating-point relaxations are disabled and NaNs canonicalized so that replay is bit-stable (REQ-SBX-008).
2. **One worker process.** `mimlys-worker` is spawned by the runtime at start and talks over its standard input and output in frames of a 4-byte big-endian length followed by one JSON object; `version` is the first field of every frame. Requests: `probe`, `execute`, `cancel`, `shutdown`; responses: `probe_result`, `execution_record`, `error`. One execution is in flight at a time (LIM-X2); `cancel` names the execution and must end it within LIM-O2. The worker's death ends the in-flight execution with `host_fault{worker_died}`, the runtime restarts the worker up to LIM-X3 times per task, and never dies with it (REQ-ARCH-008). The worker's standard error carries its log lines.
3. **Three guards, each alone.** Fuel (LIM-S1, `set_fuel`), the epoch deadline (LIM-S2 as a number of LIM-S7 ticks, driven by a ticker thread in the worker) and the memory limiter (LIM-S3, a `ResourceLimiter` that records the refusal before the trap) each end an execution on its own. The mapping to `termination` is exact: out of fuel → `fuel_exhausted`; epoch interrupt → `deadline` (or `cancelled` when the worker was asked to cancel, or `output_limit` when a stream overflowed; the worker records why it interrupted before it does); growth refused by the limiter → `memory_limit`; any other trap → `trapped{trap}`; a normal exit → `exited{exit_code}`. Nothing is inferred from timing (REQ-SBX-003).
4. **WASI boundary.** Exactly: `/workspace` preopened on the task's tree with read or read-write permission by `mode`; `/tmp` preopened on a fresh directory under the task's `tmp/` that is removed after the execution; `args` and `stdin` as declared; an empty environment; stdout and stderr into bounded buffers of LIM-S4 each; wall and monotonic clocks rounded to LIM-S6; a seeded random source in replay mode; no sockets, no other host function (REQ-SBX-004, REQ-SEC-006). Symbolic links are resolved inside the preopen only (the cap-std rule).
5. **Tools.** `run_script{language, source, stdin?, args?, mode}` writes `source` to `/tmp/main.<ext>` and runs the pinned interpreter for `language` on it; `run_wasm{module, args?, stdin?, mode}` runs a module from the workspace of at most LIM-S5 bytes. `mode = read_only` derives `workspace_read`, `read_write` derives `workspace_write`; both are `idempotent: false`. `language` is validated against the configured interpreters, so an unknown language is `invalid_argument` with the allowed list, never a failed execution. Modules are validated before instantiation; a malformed module is `host_fault{invalid_module}` (REQ-SBX-006).
6. **Interpreters, pinned and verified.** Interpreter builds are files, not code in the binary: `[interpreters.<language>]` names a `module` path and its `sha256`; the binary carries, per language, the release artifact's URL and hash of the build mimlys ships (JavaScript: a QuickJS-NG wasip1 build produced by a reproducible recipe under `tools/interpreters/`, checked in CI by hash). `mimlys interpreters install <language> [--from FILE]` verifies the hash and stores the module under `<data_dir>/interpreters/<sha256>.wasm`; a module whose hash does not match the configuration is never loaded (`host_fault{unavailable}`). Compiled artifacts (`Module::serialize`) are cached beside the module, keyed by content hash and engine version, read-only, and shared by every execution; each execution gets a fresh store (REQ-SBX-007). Python follows when a maintained wasip1 build is pinned through the same mechanism.
7. **Execution record and accounting.** Every execution reports `termination`, `exit_code` only for `exited`, and `metrics{wall_ms, fuel, memory_peak_bytes, stdout_bytes, stderr_bytes, setup_ms}` (REQ-SBX-011). A stream over LIM-S4 ends the execution `output_limit`; the bounded stream is a blob, the observation keeps the excerpt and the notice `output_truncated{total_bytes}` (REQ-SBX-005). Setup time is measured per execution and the M2 report fixes LIM-S8 and states the memory budget LIM-X2 × LIM-S3 plus the measured base (REQ-SBX-009, REQ-SCHED-003).
8. **Confinement interface, probe and tier.** `mimlys-exec::confine` defines the contract of §13.2 as a trait with one implementation per platform family and a `probe()` that returns, per clause, `enforced`, `best_effort` or `unavailable{reason}`. The worker is spawned through this interface. In M2 the portable clauses are enforced everywhere: E (an explicit, empty environment at spawn), K (the worker and anything it starts belong to a process group on POSIX and a Job Object with kill-on-close on Windows; the tree is terminated on cancel, deadline and runtime exit, and orphans of a previous runtime are terminated at startup where identifiable, REQ-CONF-009) and, on Linux, P through `no_new_privs`. F, N, M and C report `unavailable{reason}` naming the milestone of their backend (M6a, M6b, M6c); the tier is `core` and `get_runtime_status` says why (REQ-CONF-003). The WASI boundary remains the primary boundary; the outer layer adds defense in depth and arrives per platform with the backends of REQ-CONF-005, which confine the worker first and host tools second. The probe is persisted and tested for honesty with an injected failure (REQ-TEST-013).
9. **Unsafe code.** Foreign-function code lives only under `mimlys-exec/src/confine/`, each `unsafe` block justified and reviewed (REQ-CONF-010); the sandbox and the worker protocol stay free of it.
10. **Fail closed.** If the engine, the interpreter, the preopens or the confinement interface cannot be established as required, the execution ends `host_fault{unavailable}` with the reason; nothing runs with fewer guards (REQ-SBX-012).
11. **Rollback is M3.** `workspace_write` is reversible by definition (RFC 003), and in M2 the snapshot machinery that makes it so does not exist yet: a failed `read_write` execution leaves its partial writes and the observation says `rolled_back: false`. Until M3, the shipped `workspace` and `project` profiles list `run_script` and `run_wasm` in `approval_tools`, so a write by generated code passes the user's eye; M3 removes them from the defaults when rollback exists.

## Alternatives considered

- Wasmtime in the runtime process: simpler, but an engine flaw or a resource exhaustion reaches the task record and the database. Rejected (D-10).
- wasip2 components now: the interpreter ecosystem ships wasip1 modules; the component model adds a second ABI to pin and no guard. Deferred (D-16); the boundary stays thin enough to add it.
- Interpreter modules embedded in the binary with `include_bytes!`: simplest to ship, but a multi-megabyte opaque blob in the crate that reviewers cannot rebuild, and every interpreter update becomes a crate release. Rejected in favour of verified artifacts with a reproducible recipe; may be revisited if installation proves a hurdle.
- Downloading interpreters at build time or at first run without a pinned hash: supply-chain exposure (THR-12). Rejected.
- One worker process per execution: cleaner isolation between executions, but tens of milliseconds of spawn and engine setup per step against LIM-S8; a fresh store per execution gives the isolation that matters. Rejected for v1; the interface allows it later.
- Wasmtime's own on-disk compilation cache: keyed by its configuration, outside the data directory and its permissions. Rejected in favour of explicit artifacts under `interpreters/`.
- Pulling the Linux confinement backend forward into M2: the owner's environment would gain F and N earlier, at the cost of implementing a backend before the contract has been exercised by the worker on every platform. Deferred to M6a as the roadmap says; the portable clauses and the probe arrive in M2 so that nothing about the status is assumed.

## Consequences

- The security suite of REQ-TEST-008 runs on Linux, Windows and macOS in CI: each guard alone, filesystem and network denial, output limits, clock granularity, malformed modules, the worker's death, replay determinism; plus the probe's honesty.
- The M2 demonstration of external design §23: an infinite loop ends `fuel_exhausted` or `deadline` (by which limit is smaller), an allocation bomb ends `memory_limit`, a print flood ends `output_limit`, and `mimlys status` shows the tier with its reasons.
- Two new fixed vocabularies become part of the contract: the worker protocol (version 1) and the interpreter configuration. The data directory gains `interpreters/`.
- The `mimlys` command set gains `interpreters list|install` (RFC 010, M2 part); `status` gains the clause table.
- The M2 report fixes LIM-S8 and states the memory budget (REQ-SCHED-003).

## Open questions

- Whether to also publish the interpreter artifacts on crates.io as a data crate so that `cargo install` alone gives a working `run_script`; decided from the first release's feedback.
- The Python interpreter build (RustPython or MicroPython, wasip1): pinned when one has a maintained release; not blocking M2.
