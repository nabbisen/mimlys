# RFC 014 — The local daemon

**Status.** Accepted (2026-11-10, by the owner). Milestone M9, decided at 0.10's disposition point. Normative text written 2026-11-10 (requirements, limits, threat register). Drafted by the owner with the startup architect; reviewed by the architect, whose changes are marked *[review]* and argued in `.git-exclude/reviewed/rfc-013-015-review/README.md`. For the owner's sign-off after RFC 013 and RFC 015. The owner's decision of 2026-11-08: the daemon is written in this repository, not as a separate project; it is decided at 0.10's disposition point, after the audit.
**Tracks.** DR-002 (daemon mode and client sessions; superseded in part by this RFC, which needs no authentication design because the operating-system user stays the boundary); the owner's proposal `proposal-daemon-rfc.md` (2026-11-08); RFC 013 (whose admission and engine gate this RFC's scheduler absorbs).
**Touches.** `mimlys-core` (the control API unchanged; the scheduler owning LIM-X1 and LIM-X2 for all clients; sessions naming the client), `mimlys-persist` (the store's lock held by the daemon), `mimlys-exec` (no change: one worker per daemon, spawned as today), `mimlys` (a `daemon` subcommand, the socket, the client path of every command, `status`); requirements §3, §4, §15, §17, §21; external design §1, §2, §4, §16, §17, §19, §20, §21; the limits register (new LIM-O13, LIM-O14); the threat register (new THR-39).
**Release.** Not before the release after 0.10; the exact release is set when the RFC is accepted.

## Summary

One daemon per operating-system user serves the control API over a local socket to any number of `mimlys` clients of that user: a task started in one terminal is followed, approved, answered or cancelled from another, the user's tasks queue in one line under one budget, and the store has one owner. A machine without a running daemon behaves exactly as today: the client embeds the runtime. The daemon adds no network, no second user, no authentication beyond the operating system's, and no path by which a model could reach an approval. It is the same product in a second deployment shape, built from the control API, the state machine and the SPI that exist.

## Motivation

- The control API is already a boundary (REQ-ARCH-004, ED §4): requests carry a session and an idempotency id; every state change is a transition of the task state machine (RFC 001), which already models a task waiting for a human (`waiting_user`, `wait_kind`, the expiry rule). The runtime is a library the CLI embeds (RFC 010). The pieces exist; the daemon arranges them behind a socket.
- Today one process owns one store, and every command of that store is that process (RFC 013's motivation). Reading from a second terminal is solved by RFC 013; acting from one (approve, answer, cancel, grant) is not, and cannot be without one owner of the running task.
- Machine-wide bounds in RFC 013 are an agreement between independent processes through a registry. A daemon replaces the agreement with one scheduler: one line of tasks, one count of executions, one gate per engine, in one place that `status` can show without guessing.
- A separate project for the daemon would duplicate or vendor the validator, the policy, the persistence and the confinement; INV-01, INV-10 and INV-13 would then exist twice and drift. rypsok is separate because it is a different trust domain; the daemon is not.

## Decision

1. **Two deployment modes, one product (REQ-ARCH-009, new).** *Embedded*: the client process contains the runtime, as today. *Served*: a daemon of the user owns the store and the runtime; the client sends control-API requests over a local socket. Every rejection code, event, state, `--json` field and message means the same in both modes (REQ-MAIN-001). `status` says which mode is in force and, when served, the daemon's pid, uptime, socket and clients.
2. **One daemon per user and per data directory.** The socket lives under the user's runtime directory, named from a hash of the data directory's canonical path (*[review]* a Unix socket path is limited to about 104 bytes, so the path itself cannot be the name), so a user with two stores has two daemons; RFC 013's registry knows them. The daemon takes the store's exclusive lock (REQ-PERS-014, new): a client that holds the lock in embedded mode and a daemon never coexist on one store; whichever is second says who holds it and exits.
3. **Transport and identity (REQ-SEC-016, new).** A Unix domain socket with mode 0600 in a 0700 directory, and a peer-credential check (`SO_PEERCRED` on Linux, `LOCAL_PEERCRED` on macOS) that refuses any uid but the daemon's; on Windows a named pipe whose DACL admits the user's SID alone, with the client's identity read from the pipe. No TCP, no port, no environment variable that could point a client elsewhere. The protocol is the control API's request and response types over the worker's length-prefixed JSON framing (RFC 005), with the decision schema version in the handshake; a client and a daemon of different runtime versions refuse each other and say which to restart.
4. **Sessions name the client (ED §4, amended).** A session is the client's pid and user as today, carried by the daemon into every event and grant it records (`session: "pid:<client pid>"`, `os_user`), so the audit says which terminal approved what. Idempotency by request id is unchanged.
5. **Authority stays with the human at a client.** Approvals, answers, grants and cancellations are requests a client sends; the daemon records `waiting_user` and the expiry as today and never answers for anyone. The daemon has no interface a model can reach: the worker speaks only the worker protocol, the MCP servers only MCP, and neither is given the socket's path (INV-13 holds by construction, not by filtering).
6. **One scheduler, one budget (REQ-SCHED-008, new).** LIM-X1 and LIM-X2 become the daemon's counts over all clients' tasks: one line of tasks in `created` with the queued flag, one count of executions, and the engine gate of RFC 013 inside the daemon. RFC 013's registry then records only that a daemon serves this store; clients take no slots. Whether LIM-X1 may exceed 1 under the daemon is a later decision with its own measurement; this RFC keeps the values. *[note 2026-11-12, handoff 002d review]* Today one task's steps are serialised only by their one driver, `run_until_wait`, which awaits each step; nothing in `Runtime::run_step` refuses two overlapping calls for one task, and the step index (`load_steps().len()`) would not catch them. The daemon's handoff says who serialises a task's steps: the scheduler, or a per-task guard in the runtime.
7. **Lifecycle (REQ-CLI-008, new).** `mimlys daemon start | stop | status`. A client that finds no daemon for its store runs embedded, as today; the user starts a daemon on purpose, or sets `[runtime] serve = on_demand` to have the first client start one that outlives it. `stop` finishes or checkpoints the running execution within LIM-O2, refuses new requests with `stopping`, then exits. A daemon idle for **LIM-O13** (candidate 30 min, configurable, `never` allowed) exits by itself and says so in the log. A client finding a socket whose daemon is dead reaps it (lock free, pid gone) and reports `daemon not running` rather than hanging; a connect waits at most **LIM-O14** (candidate 2 000 ms).
8. *[review]* **What the daemon's environment and configuration are.** The daemon reads the configuration and resolves every `env:` reference when it starts, from its own environment. A client never sends its environment or its configuration. `status` shows the daemon's start time and the hash of the configuration it read. A client whose configuration file hashes differently says `the daemon runs an older configuration: restart it with mimlys daemon stop`, rather than letting a user believe an edit took effect. A changed secret needs a restart too, and the book says so. Started on demand, the daemon detaches from the client's terminal and session (`setsid`; on Windows a detached process), so closing the terminal does not end it.
9. **Recovery.** A daemon's crash leaves the store in the states REQ-PERS-007 and REQ-PERS-008 already guarantee; the next daemon or embedded client recovers them and `status` lists what it recovered, as today. A client's exit never cancels a task (`run` prints how to follow and how to cancel); cancellation is always explicit.
10. **Observability.** The daemon's log is the runtime's log, in a file under the data directory with the rotation the configuration sets; `mimlys daemon status` tails it on request. Metrics gain queue length, wait per task, clients connected. Events gain `client.connected` and `client.disconnected` with the session (ED §17).
11. **Windows.** The daemon is the process that creates the AppContainer, the token and the Job Object for the worker (RFC 011 §3, §7), as the runtime does today; nothing moves to the client. The named pipe's DACL and the container's lowbox token are unrelated: the worker is never given the pipe.

## Alternatives considered

- **A separate project.** Rejected by the owner (2026-11-08): duplication of the safety core, drift of invariants, two release lines for one contract.
- **TCP on loopback with a token.** Simpler to write portably, but it creates a credential to manage (DR-002's "authentication design"), a port to collide on, and a path that a misconfiguration can expose. The operating system's user boundary is already what every other control trusts. Rejected until a real need for remote clients exists; that would be a new RFC and a new trust model.
- **Keep the registry of RFC 013 and no daemon.** It answers resource bounds but not acting from a second terminal, and its agreement between processes is weaker than one owner. Kept as the bridge and the fallback mode.
- **Several daemons per store (one per project).** The store is the unit of consistency (snapshots, reference counts, the worker record); two owners would need the locking this RFC avoids. One daemon per store.
- **The daemon as a system service for all users.** Multi-user is DR-003 and needs isolation this RFC does not design. Out.

## Consequences

- Served mode: approve, answer, grant, cancel and follow from any terminal of the user; one queue and one budget for the user's tasks; a store with one owner.
- New: a subcommand, a configuration key, two LIM entries, two events, metrics, `status` fields; the session field gains nothing new in shape. Additions under REQ-MAIN-001. Embedded mode stays supported as long as the project lives.
- The socket is a new local attack surface, confined to the user (THR-39, new: another process of the same user drives the daemon; controls: the credential check, 0600, the audit naming the client's pid; residual: a same-user process has the user's authority already, as it has over the user's files).
- RFC 013's decisions 5 and 7 are absorbed when a daemon runs; their words, events and ids stay, so a user moving between modes reads the same `status`.
- The book gains a page "Running mimlys as a daemon" with the two modes side by side and the one table that explains queued reasons across both.

## Open questions

1. Should `run` in served mode return as soon as the task is created (printing how to follow), or follow by default as today? The proposal is to follow by default with `--detach` to return, so that the embedded and served modes feel the same.
2. The approval prompt when no client is attached: queued until a client attaches, with the expiry unchanged? Proposed yes; `status` lists pending approvals first, and `mimlys daemon status` names them.
3. One binary with a subcommand, or `mimlysd`? Proposed one binary, one installation; the daemon is `mimlys daemon`.
4. Whether the on-demand start should be the default once the daemon has shipped a release without defects, or stay opt-in.
5. The Windows named pipe's exact ACL and whether a service account variant is ever wanted (it would be DR-003).
