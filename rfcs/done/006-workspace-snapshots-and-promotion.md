# RFC 006 — Workspace snapshots, rollback and promotion

**Status.** Implemented (0.7.0; accepted 2026-10-28)
**Tracks.** Decisions D-08 and D-09 of the startup review; findings R-09, R-10, R-12, R-13, A-05, A-12, X-04; threats THR-07, THR-08, THR-27, THR-28, THR-29.
**Touches.** `mimlys-core` (the snapshot manifest and diff as pure types, the `WorkspaceProvider` SPI, the loop's write-effect lines, recovery with restore, fork), `mimlys-persist` (the snapshot store with its journal, migration 002, task deletion), `mimlys` (restore, promotion, fork, `rollback`, `promote`, `task delete`, `task new --from-task`), external design §5.4, §7.5, §14.3 … §14.6, §16.3, §16.4, §19.1, §19.2; requirements REQ-WS-009, REQ-WS-012, REQ-PERS-010, REQ-OBS-005 (amended: explicit deletion instead of timed collection).

## Summary

Make every write-effect action a transaction over the workspace: a content-addressed snapshot before it, a snapshot after it when it succeeds, and a restore of the pre-execution snapshot before its observation when it fails, is cancelled, or is found running after a crash. Make promotion the only path into the user's project: a diff against the base snapshot, a refusal on conflicts, a backup of the targets, the user's confirmation, then the writes. Give every stored thing an owner and an explicit end: a task's workspace, snapshots and blobs leave the disk when the user deletes the task, never by a timer or a collector; a crash leaves nothing behind because a snapshot is written as a journaled transaction that the next start completes or undoes. Fork from a snapshot.

## Motivation

- "Transaction equals action" (REQ-TOOL-010) was promised in M1 and M2 but every failed write so far left its partial state in the workspace, with the observation saying `rolled_back: false` and the shipped profiles asking the user before every script as a stopgap (RFC 005 §11).
- Recovery after a crash restores nothing yet (handoff 004); a write found running becomes `unknown` and the task halts `recovered` with the workspace as the crash left it (R-11, THR-29).
- Nothing reaches the user's tree today, which is safe but useless: promotion needs its diff, its conflict rule, its backup and its audit (D-09, R-10, THR-28).
- Symbolic links are the classic way out of a sandboxed tree; snapshot, restore and promotion must each refuse to follow them (R-09, THR-27).

## Decision

The normative text is external design §5.4 (fork), §7.5 (dispositions), §14.1 (layout), §14.3 … §14.6 (snapshots, rollback, promotion, quotas and lifecycle), §16.3 (recovery), §16.4 (retention), §21.3 (CONS-04), and requirements REQ-WS-004 … REQ-WS-007, REQ-WS-009, REQ-WS-010, REQ-WS-012, REQ-TOOL-010, REQ-PERS-007 (M3 part), REQ-PERS-009, REQ-PERS-010, REQ-PERS-011, REQ-TASK-004, REQ-OBS-005, REQ-SEC-015, REQ-TEST-009. In brief:

1. **Snapshot = manifest + objects.** Objects live at `<data_dir>/snapshots/objects/<sha256>` once per content, written through a temporary name, fsynced, renamed, then made read-only. A manifest lists the tree's entries sorted by path: `file{path, executable, size, hash}`, `dir{path}`, `symlink{path, target}`; it is JSON at `<data_dir>/snapshots/manifests/<snapshot_id>.json`, fsynced before the database row that references it, and the row carries the manifest's own hash (REQ-PERS-009; CONS-04 checks it). Links are entries, never followed; excluded paths (LIM-W4, LIM-W5) never appear.
2. **When.** `base` at materialization; `before` every action with a write effect (its id goes into the authorized record, persistence line 4); `after` every successful write action (into the execution record, line 6). Two consecutive snapshots with the same manifest hash are one snapshot. Quota (REQ-WS-008) is read from the `after` manifest at the step boundary: above LIM-W1 or LIM-W2 the task halts `workspace_quota`.
3. **Every snapshot hashes every file.** No index, no modification-time heuristic: a snapshot's correctness never depends on a filesystem's clock or on a guess about what changed, so a restore and a promotion diff can never miss a modified file. The cost is one walk and one hash of the tree per snapshot (about a second per gigabyte on the reference machine) and the M3 report measures it; the object store deduplicates by content so unchanged files cost a hash and nothing else. Exact change tracking through the tools, if it is ever needed for speed, is a later RFC; a heuristic index is not.
4. **Rollback.** `restore(task, snapshot)` makes the tree equal to the manifest: entries absent from it are deleted, objects are verified by hash as they are copied in (a copy, reflink where the filesystem offers it, never a hard link into the writable tree), directories are created, symbolic links are recreated only when their target is relative and stays inside the root (an escaping target is refused and reported as `symlink_omitted`), and the index is rebuilt. The event `workspace.rollback{snapshot_id}` is recorded. Automatic restore happens before the observation of a failed write execution (`rolled_back: true`, REQ-TOOL-010), after a cancelled write execution unless the profile says `on_cancel = keep` (the observation says which, REQ-WS-010), and at recovery for a write found running (REQ-PERS-007: restored → `halted(recovered)`; a restore that fails → `halted(unknown_outcome)`). `rollback_workspace{task, snapshot?}` is the user's verb, valid when the task is not `running` or `recovering`; it defaults to the latest snapshot.
5. **Promotion is the only exit (INV-10, REQ-SEC-015), with a patch as the way around it.** `promote_workspace{task}` is valid when the task is not `running` or `recovering`. It rehashes the workspace, computes `diff(base, current)` as added, modified and deleted paths, drops excluded paths with a notice, and compares every target in the project scope with the base entry: a target that differs from the base (or exists where the base had nothing, or is missing where the base had a file) is a conflict, and conflicts refuse the whole promotion with their list. Otherwise the diff is shown (a unified text diff for files under LIM-W3 that are valid UTF-8, a size line for the rest), the user confirms (the prompt, or `--yes` without a terminal), the targets' current versions are backed up into a `backup` snapshot recorded with the project root, the files are written through temporary names and renamed, deletions applied, and `workspace.promoted{files}` recorded with the promotion row. A promotion is reversed by `rollback --promotion` from its backup snapshot. `promote --patch` prints the same diff as a unified patch on standard output and writes nothing, for the user who wants to apply it by hand or elsewhere (the "emit patch" alternative of D-09). Symbolic links are promoted as links only when relative and inside the scope; the model cannot propose promotion in v1.
6. **Ownership instead of collection.** Everything on disk belongs to one task: its workspace, its snapshots (and, through a reference count kept in the same transaction as the snapshot row, the objects its manifests use), its blobs, its promotion backups. Nothing expires and nothing is swept. A workspace is `allocated` at creation, `active` after materialization, `archived` when its task is terminal (the tree and the snapshots stay, so the user can inspect, roll back, promote or fork), and `deleted` when the user runs `mimlys task delete <task>`, valid for a terminal task only: it removes the workspace, the snapshots whose objects' counts reach zero, the blobs and the backups, keeps the audit events (`--audit` removes those too), tells the user beforehand what will go (including that a promotion can no longer be reversed) and asks for confirmation (`--yes` without a terminal). `task list` and `status` show each task's footprint and the data directory's total, so the user sees what is kept and decides. A snapshot is written as a journaled transaction: a journal under `snapshots/pending/<snapshot_id>` names the objects it adds; the row is recorded, then the journal removed; at startup a journal without a row is undone (its new objects unlinked) and one with a row is finished (removed), so a crash never leaves an orphan and nothing needs collecting (ED §16.3 amended). The limits LIM-P2, LIM-P3 and LIM-P4 become "no timer; explicit deletion" and `[workspace] retention_days` is removed from the configuration (an unknown key, refused with the message that names `task delete`).
7. **Fork (REQ-TASK-004).** `create_task{from_task, from_snapshot?}` materializes the new workspace by restoring the chosen snapshot (default: the source's latest) into a new tree, records it as the new task's `base`, copies the source's active grants (shown at creation, never widened), and attaches the source's goal, plan and the last LIM-C5 steps (decision and outcome, no file content) as a read-only `history` segment of the context. The source is untouched.
8. **Backup (REQ-PERS-011).** The data directory is self-contained; copying it while the runtime is stopped is a complete backup, and the book says so.
9. **The M2 stopgap ends.** With rollback in place the shipped profiles no longer list `run_script` and `run_wasm` in `approval_tools` (RFC 005 §11; REQ-SEC-014).

## Alternatives considered

- Git as the snapshot store: an external binary, poor with binaries and large files, and it collides with the project's own `.git`. Rejected (D-08).
- Hard links from the object store into the workspace: fast, but a write through the link would corrupt the object. Rejected; copies, reflinks where available.
- Snapshot only the files a tool reports touching: the sandbox cannot report; the index makes whole-tree snapshots cheap enough. Rejected.
- Promotion that merges on conflict: a three-way merge silently changes the user's edits. Rejected; conflicts refuse, the user resolves.
- An index of modification times to skip unchanged files: one walk plus the changed files per snapshot, but a file rewritten within the clock's granularity with the same size would keep a stale hash, and a restore or a promotion could then miss a change. Rejected: a snapshot's truth must not depend on a heuristic.
- Timed retention and a `gc` command (the drafts' model): deletions the user did not ask for, at a moment the user did not choose, and a collector that must be trusted never to take the wrong thing. Rejected in favour of ownership, explicit deletion and a journal that leaves no orphans; the owner's preference, and the clearer model for the user.

## Consequences

- Every write action costs two hashes of the tree; measured in the M3 report together with restore times.
- Migration 002 adds `snapshots`, `objects` (reference counts), `workspaces` and `promotions`; integrity gains CONS-04 and the rule that every object row's count equals its manifests' references.
- The `WorkspaceProvider` SPI grows `snapshot`, `restore`, `diff`, `promote`, `materialize_from`, `delete`; the fakes follow.
- `rollback` and `promote` leave the "available from M3" list; `gc` is withdrawn from the command set and replaced by `task delete`; `task new` gains `--from-task` and `--from-snapshot`; `task list` and `status` gain the footprint.
- Requirements REQ-WS-009, REQ-WS-012, REQ-PERS-010 and REQ-OBS-005 are amended from timed retention to explicit deletion; LIM-C5 (forked history steps shown) is added; LIM-P2 … LIM-P4 are marked "no timer"; `[workspace] retention_days` is removed.

## Open questions

- Whether the hashing cost on large trees calls for exact change tracking through the tools (an own RFC); decided from the M3 report.
