# RFC 009 — The MCP client and tool pinning

**Status.** Implemented (0.7.0; accepted 2026-10-29). **Pin moved, 2026-11-10:** `rmcp =3.5.0` became `=3.9.0` (handoff 009b: RUSTSEC-2026-0457, -0461 and -0462, none in a feature mimlys enables); still exact, same features, no behaviour change, the M5 suite unchanged. The `=3.5.0` below is the text as accepted
**Tracks.** Decision D-13 of the startup review; findings M-06, K-01 … K-07, K-10, R-07, R-08; threats THR-10, THR-24, THR-25, THR-26.
**Touches.** `mimlys-mcp` (the client: child processes, discovery, import, calls, cancellation), `mimlys-core` (external tools in the ceiling, output validation of imported schemas, `tool.pinned`/`tool.unpinned` emitted), `mimlys` (`[servers.<name>]`, the tools composed per task, `status`), external design §3, §11.1, §17.1, §19.1, §20, §23 (M5); requirements REQ-MCP-001 … 010, REQ-TOOL-005, REQ-PRIV-003, REQ-TEST-012.
**Reference contract.** rypsok 0.7.0 (rypsok 0.8.0, 2026-10-29, is contract-compatible: the three response schemas and the `rmcp =3.5.0` pin are unchanged; what changed are `web_fetch`'s error kinds and reasons, which mimlys surfaces as `kind: message` without interpreting them, so nothing depends on them; verified 2026-11-03) (`.git-exclude/projects/rypsok`, tag 0.7.0): tools `web_search`, `web_fetch`, `engine_status`; MCP over stdio (and Streamable HTTP, not used here); the handshake-based revisions and 2026-07-28 served in parallel; `notifications/cancelled` honoured within 500 ms; graceful exit on closed stdin within 3 s; `structuredContent` plus the same JSON as text; errors as `isError: true` with one `{error: {kind, message, detail}}` object; annotations `readOnlyHint: true`, `idempotentHint: true`, `openWorldHint` per tool; server instructions one paragraph.

## Summary

Run each configured MCP server as a child process with an allow-listed environment and secrets by reference, started lazily within LIM-O6 and ended at runtime exit. At task creation list its tools, import each definition under bounds (description sanitized and cut to LIM-I2, at most LIM-I3 parameters, depth LIM-I4, the output schema kept whole for validation), take the effect from the administrator's declaration and never from the server's annotations, hash and pin every definition on the task, and show the model only the tools it holds a `tool` grant for. Validate destination arguments against `network` grants before every call; never follow a redirect. Call with a per-tool deadline (LIM-O5 by default, never below a configured server maximum), cancel with `notifications/cancelled` and kill the server if it does not stop within LIM-O2 (LIM-X3 restarts per task). Validate `structuredContent` against the pinned output schema, turn `isError` into `tool_error` with the server's error kind as the detail, bound the content and label it external. A definition that changed since pinning makes the tool unavailable for that task with `tool.unpinned` until a new task pins it. mimlys exposes no MCP server (REQ-MCP-010).

## Motivation

- The study's whole purpose for external integration is rypsok: search and reading without a browser in the runtime (D-13: no built-in network adapter; every egress through an external tool under a `network` grant).
- Tool descriptions enter the prompt and annotations are server-asserted (R-08, THR-25, THR-26): the runtime must bound, sanitize, pin, and take effects from its own policy.
- API keys for engines live in the operator's environment (R-07, THR-24): children must start from an explicit environment.
- rypsok's contract is now stable enough to build on (0.7.0, with a stability page from 1.0.0), and it ships committed example transcripts that make a faithful test server cheap.

## Decision

The normative text is external design §11.1 (external tools), §19.1 (`[servers.<name>]`), §17.1 (`tool.pinned`, `tool.unpinned`), §20, requirements REQ-MCP-001 … REQ-MCP-010, REQ-TOOL-005, REQ-PRIV-003, limits LIM-I1 … I4, LIM-O2, LIM-O5, LIM-O6, LIM-X3. In brief:

1. **Servers are children (REQ-MCP-001, REQ-PRIV-003).** `[servers.<name>]` declares `command`, `args`, `env_allow` (names copied from the runtime's environment; nothing else is inherited), `env_secrets` (name → `env:`/`file:` reference, resolved at start and placed in the child's environment and in the redaction set of RFC 007), `startup_ms` (LIM-O6) and optional `max_call_ms` (the server's declared maximum, below which no tool deadline may fall). The server starts at the first need (task creation or a call) within LIM-O6, speaks MCP over its stdin and stdout through the pinned SDK (`rmcp =3.5.0`, the version rypsok itself pins; features `client`, `transport-child-process` only), is ended at runtime exit by closing stdin and, after LIM-O2, by terminating the process group or Job Object (the portable E and K clauses of RFC 005). A server that dies is restarted at the next need, at most LIM-X3 times per task; beyond that its tools fail `host_fault{server_died}` for that task. Standard error is logged at `info` through the redactor; standard output is protocol only.
2. **Discovery and import (REQ-MCP-002, REQ-MCP-003).** At task creation the runtime lists the tools of every configured server (`tools/list`) and imports each as `<server>.<tool>`: the description sanitized (REQ-CTX-008) and cut to LIM-I2 with a `description_truncated` note in the definition's import record; the input schema converted to the flat parameter model (string with bounds, integer with bounds, boolean, enum, string array, one nested object; `additionalProperties: false` assumed; `default` values kept as documentation only); a schema with more than LIM-I3 parameters, deeper than LIM-I4, or using a construct outside that model makes the tool **unavailable with a reason** (`schema_unsupported{parameter, construct}`), listed by `status`, never shown to the model; the output schema is kept whole (the server's JSON Schema) for validation; annotations are recorded in the import record and used for nothing. The server's `instructions` are recorded and not placed in the context (the runtime's own instructions already say that labelled segments are data). Every imported definition is hashed (LIM-U6) and pinned on the task with `tool.pinned{tool, hash}`.
3. **Effects come from the administrator (REQ-MCP-004).** `[servers.<name>.tools.<tool>]` declares `effect` (`external_read` or `external_write`), `idempotent`, `destination_arguments` (parameter names holding URLs) and `timeout_ms`. An undeclared tool is `external_write`, not idempotent, no destination arguments, LIM-O5: the most restrictive reading, so it needs approval under every shipped profile's derivation (RFC 003) and is visible only with an explicit grant. `reversible` is always false for external effects (RFC 003's declaration rule). A declaration naming a tool the server does not list is a configuration warning in `status`, not an error (the server may gain it later).
4. **Visibility and the ceiling (REQ-MCP-009).** An external tool is visible to the model only with a `tool` grant for `<server>.<tool>`. It is grantable (in the ceiling) when the administrator **declared it** under `[servers.<server>.tools.<tool>]`, or named it in `policy.ceiling.tools` (then it runs under the restrictive defaults of point 3, and `check` says so). The declaration is the administrator's admission: one block to write, then a profile line or a grant; `check` and `status` print the effective ceiling with the source of every external entry. The shipped ceiling and profiles list no external tool; `rypsok.engine_status` stays invisible unless declared or listed and then granted (K-04).
5. **Destinations (REQ-MCP-005, D-13).** Stage 7 validates every `destination_arguments` value against the task's `network` grants (scheme `https`, host suffix, port) before the call, as it does today; the runtime never follows a redirect: rypsok returns `redirected{location}` as a tool error, the model may call again with the new URL, and that call is validated like any other. A `web_fetch` to an ungranted host is `denied` before anything leaves the host (external design §23, M5).
6. **Calls (REQ-MCP-006, REQ-MCP-007, REQ-MCP-008, REQ-TOOL-005).** One `tools/call` per execution with the canonical arguments, under the deadline of REQ-TOOL-006 (the declared `timeout_ms`, the task's remaining time, the profile's cap; never below the server's `max_call_ms`). The result: `structuredContent` validated against the pinned output schema with a bounded JSON-Schema validator (the constructs rypsok's generated schemas use: `type` incl. arrays of types, `properties`, `required`, `additionalProperties`, `items`, `enum`, `const`, `anyOf`, `oneOf`, `$ref` into `$defs`, `minimum`/`maximum`, `minLength`/`maxLength`; `format` is ignored); a violation is `output_invalid` and the content is not passed; a result without `structuredContent` uses `content[0].text` parsed as JSON when the schema demands an object, else the text is the payload's `text` field. `isError: true` is `tool_error{kind}` with the server's `error.kind` and `error.message` (bounded to LIM-I5) as the detail, and `error.detail` kept in the payload: the model reads `invalid_request`, `denied`, `unavailable{retry_after_ms}`, `redirected{location}`, `unsupported_content`, `too_large` exactly as rypsok's integration guide intends. Every string of the payload is sanitized and bounded (LIM-C2 ceiling per string; a cut adds `content_truncated`), the observation is labelled `observation tool="rypsok.web_search"` like every other, and rypsok's own `notices` stay inside the payload as external-asserted data. Cancellation sends `notifications/cancelled`; if the server has not answered within LIM-O2 it is killed (restart bounded by LIM-X3) and the execution ends `cancelled`.
7. **Pinning holds (REQ-MCP-002).** A definition can change only when the server restarts or announces `notifications/tools/list_changed`; both mark the server's list dirty. At the next step boundary the runtime refreshes a dirty list and compares each hash with the pinned one: a changed tool is unpinned there, with `tool.unpinned{tool}` once, omitted from the visible definitions, and named to the model in a runtime `feedback kind="tool_unavailable"` segment with the reason `definition_changed` and the hint that a new task pins the new definition. The model never proposes a tool that no longer exists as pinned; if it does, stage 1 rejects `unknown_tool` as for any unlisted tool. As a second line, the client compares the hash again at call time and fails `tool_error{definition_changed}` on the rare race. Definitions never change silently inside a task.
8. **Status.** `status` lists every configured server with `running`/`stopped`, the SDK's negotiated revision, the server's `name`/`version`, the tools imported, the tools unavailable with their reasons, and the declarations that name no listed tool.
9. **No server surface (REQ-MCP-010).** mimlys is an MCP client only.

## Alternatives considered

- A hand-written JSON-RPC client over stdio instead of `rmcp`: fewer dependencies, but a second implementation of the handshake, the revisions and cancellation that rypsok's own SDK already provides; pinning the same version as rypsok keeps the pair in step. Rejected; the SDK stays outside `mimlys-core` (REQ-ARCH-002).
- Trusting `readOnlyHint`/`idempotentHint`: the server asserts them and a hostile or mistaken server would make a destructive tool look safe (THR-26). Rejected (K-06).
- Importing input schemas as opaque JSON Schema: the model would see schemas the validator cannot enforce. Rejected; the flat model with a clear `schema_unsupported` reason, and the full schema only for output validation where the runtime, not the model, is the consumer.
- Following redirects in the runtime: would move destination policy into the client. Rejected (D-13): the model re-proposes and stage 7 validates.
- Refreshing definitions per step: would let a server change a tool's meaning mid-task. Rejected (THR-25): pinned until a new task.

## Consequences

- `mimlys-mcp` gains `rmcp =3.5.0` (`client`, `transport-child-process`); `mimlys-core` gains a bounded JSON-Schema validator for outputs and the import record on the task's versions (`tool_imports`: per external tool the server, the hash, the annotations, the truncation and the unavailable reason).
- Configuration: `[servers.<name>]` with `command`, `args`, `env_allow`, `env_secrets`, `startup_ms`, `max_call_ms`, and `[servers.<name>.tools.<tool>]` with `effect`, `idempotent`, `destination_arguments`, `timeout_ms`; `policy.ceiling.tools` may name external tools.
- Events: `tool.pinned` and `tool.unpinned` emitted (they exist in the vocabulary); `server.started{server, version}` and `server.stopped{server, reason}` added. Context: the runtime feedback kind `tool_unavailable{tool, reason}` (RFC 007's segment vocabulary grows by one kind).
- Tests (REQ-TEST-012): a local test server speaking rypsok's protocol and answering from rypsok's committed example transcripts (`examples/calls/*.json`) exercises pinning, environment scrubbing (a tool that echoes its environment shows no operator secret, REQ-TEST-015), output-schema validation, cancellation, destination validation, hostile descriptions, undeclared-effect defaults, server death and restart, and a changed definition. The M5 demonstration runs against a real `rypsok serve` when the binary is present (`MIMLYS_RYPSOK_BIN`), with its Wikipedia engine pointed at a loopback fixture server the way rypsok's own tutorial test does.
- Documentation: the book gains "External tools: rypsok" (install, the three configuration lines, a first search, what `denied` and `redirected` mean, `engine_status` kept from the model).
