# Changelog

All notable changes to mimlys are recorded here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versions follow
semantic versioning; tags carry no `v` prefix. Before 1.0.0, a change to the
external contract (task states, decision fields, tool names and schemas,
effects, rejection codes, event names, CLI commands, JSON output fields) is
announced here under "Changed".

## [Unreleased]

### Added

- `mimlys-persist`, `mimlys-core`, `mimlys` (RFC 013 part one, handoff 013-1; REQ-PERS-013): the **read-only open of the store**. `status`, `events` (and `--follow`), `metrics`, `task list`, `task show`, `toolchain list` and `promote --patch` open the database as a WAL reader through a handle (`ReadStore`) that takes no lock on `mimlys.lock` and runs no recovery, integrity check, reaping of a leftover worker or migration, records no `runtime.started` event and creates no directory, and that has no writing method: `Persistence` is now `PersistenceRead` plus the writing methods and `WorkspaceProvider` is `WorkspaceRead` plus the rest, so a read command cannot call a write. A second terminal can therefore watch a task another process runs; a reader never says "locked". `status` gains the store line: `store: in use by runtime <pid> since <time>` (the writer records itself in the new file `mimlys.holder`, because a held lock is mandatory on Windows and a reader could not read the lock file), `recovery pending: the next command that writes recovers it` (the lock is free and a task is still `running`; what is committed is read as it stands), or `store: not created yet`. A schema newer than the reader knows is refused with the reason; an older one says `migration pending`; neither is migrated. The commands that write keep the exclusive open and its wait (LIM-O3). `events --follow` of a task whose runtime is gone says `recovery pending` and ends instead of waiting for ever. `promote --patch` is read-only (the plan reads and writes nothing); `rollback` has no dry run and always restores, so it is not.
- `mimlys`, `mimlys-exec`, `mimlys-core` (RFC 013 part one, handoff 013-2; REQ-WS-013): **`mimlys status --storage`**: the store's path, its filesystem and whether it can reflink (`yes`, `no`, `unknown`, judged from the filesystem's type; `mimlys-exec::fsinfo` reads `/proc/self/mountinfo` on Linux, the output of `mount` on macOS and asks the volume on Windows), the bytes by kind (working trees, snapshot objects exclusive and shared, blobs, interpreters, database and WAL, temporary) and the tasks that hold the most with state, age and what deleting each frees. Read-only. The numbers come from the store's records (each task's latest non-backup snapshot for its tree, the manifests' object lists and ownership, the blob rows); only `tmp/`, the interpreters and the database files are measured on disk, and no working tree is walked.
- `mimlys` (RFC 013 part one, handoff 013-3; REQ-WS-014): **`mimlys task prune [--state STATES] [--older-than D] [--audit] [--yes]`**: lists the finished tasks that match with their footprints and the total, asks once, then deletes each through the path of `task delete`, one at a time, reporting each result. It never lists a task that is not terminal, keeps a task whose promotion is still reversible (`kept: promotion reversible`), keeps audits unless `--audit`, does not list a task already deleted again (unless `--audit`), and on a failure stops, names the failed task and the tasks it did not touch (exit 1, `--json` with `failed` and `untouched`).

### Changed

- **The read commands no longer record `runtime.started` and `runtime.stopped`, and no longer wait for the lock** (RFC 013, REQ-PERS-013). `status`, `events`, `metrics`, `task list`, `task show`, `toolchain list` and `promote --patch` used to take the store's exclusive lock, run recovery, reap a leftover worker and record the two events; now they do none of these. A store left by a runtime that ended mid-task stays as it was until the next command that writes. `status` creates no data directory; `status` starts the configured MCP servers to list their tools, as before, but records nothing of it; **with no data directory yet it starts none**, because a server's working directory is the data directory and a read command must not start one anywhere else: it prints `servers: not started (no data directory yet)` and lists each server's declared tools as declared.
- **Public API of the library crates** (RFC 013, for library users): the `Persistence` trait of `mimlys-core` is split into `PersistenceRead` (the reading methods) and the writing methods, and `WorkspaceProvider` into `WorkspaceRead` and the rest; code that implemented or called them as one trait names the half it needs. `PersistenceError` gains the variant `MigrationPending` (a reader met a schema older than it knows; it migrates nothing). The CLI and the stored data are unchanged by the split.
- **Additive fields of the external contract** (RFC 013; no schema version changes): `status` gains `store` (`state` `free`, `in_use`, `recovery_pending`, `absent` or `lock_untested`, and `holder: {pid, since}` when another runtime holds the store); `status --storage` and `task prune` print the objects listed in the command-line reference. `status`'s `recovered` stays and is always empty. New file in the data directory: `mimlys.holder`. In `status`, a server's `state` can be `not_started` (no data directory yet), with `detail: "no data directory yet"` and the new field `declared` (the declared tools, full names; absent otherwise). New error variant `PersistenceError::MigrationPending`.

### Documentation

- A "Storage" page (what lives where, reflinks per filesystem, what grows, how to reclaim), a section "Several projects, several jobs" in Getting started (one store per user; a second terminal can watch; two runtimes on two data directories do not know each other; the two reasons a task waits), and the command-line reference for `status --storage`, `task prune` and the read commands (REQ-CLI-007). The commands in the tested blocks of those pages run in the test suite.

## [0.9.0] - 2026-11-10

0.9.0 completes RFC 012: mimlys asks the model for its decision through the engine's native function calling, and one local model, Qwen2.5-7B-Instruct (Q4_K_M), was measured to finish the M4 task (9 of 10 runs: 4 of 5 on llama.cpp, 5 of 5 on Ollama; one model, one task, one machine; the M4 report, §7). The decision envelope of 0.8 stays as `decision_transport = "envelope"`, and the twelve validation stages are unchanged.

### Added

- `mimlys-core`, `mimlys-model`, `mimlys` (RFC 012, handoff 012-1; REQ-MDL-009, REQ-DEC-003 amended, REQ-MDL-004): decisions as **native tool calls**. `[backend] decision_transport = "auto" | "tool_calls" | "envelope"` (default `auto`). With `tool_calls` every pinned tool is offered as one function (its name with `.` written `__`, matching `^[A-Za-z0-9_-]{1,64}$`; the parameters a JSON-schema object generated deterministically from the tool's definition, which and whose hash are not changed) beside the four reserved functions `plan`, `ask_user`, `complete` and `give_up`; a tool whose function name is invalid, reserved or equal to another's is unavailable in this transport and named to the model with the reason. The decision is the reply's structured `tool_calls`: exactly one entry naming an offered function with one JSON object (within LIM-D1) as its `arguments`, mapped onto the existing decision envelope before stage 1 of the twelve validation stages, which are unchanged. No call, several, an unknown name, arguments that are not one object, or a call only written into the text are `malformed` and consume the rejection counter; nothing is repaired and **a call in the text is never read**. Text beside a structured call is neither parsed nor put into the context; its length is recorded. The request sends `parallel_tool_calls: false` where the engine accepts it and no `tool_choice`. The probe in `status` sends one request with one function: HTTP 200 resolves `auto` to `tool_calls`; a refusal (llama.cpp without jinja: HTTP 500 `tools param requires --jinja flag`) resolves it to `envelope` with the engine's reason; `tool_calls` configured and refused is `backend_unavailable` with the reason, never a silent fallback; a probe that times out says `timeout (the model may still be loading)`. `structured_output` applies to the envelope transport only. The new fields of `status` and of `decision.received` are listed once, under Changed. SPI: `Role::Tool`, `Message.call` and `call_id`, `GenerateRequest.transport` and `functions`, `ModelBackend::decision_transport` and `last_text_chars` (defaults keep a backend on the envelope).

### Changed

- **Upgrading: with the default `decision_transport = "auto"`, the request to the model changes shape** (RFC 012). If the engine accepts `tools` (the probe in `status` sends one request with one function), mimlys now offers the tools as functions and reads the decision from one structured tool call; the messages, the instructions and what the context budget counts change with it. An engine that refuses `tools` (llama.cpp started without `--jinja`) stays on the envelope, and `status` says so with the engine's reason. To keep 0.8's request exactly, set `decision_transport = "envelope"`. A model that does not return structured calls (the Qwen2.5-Coder variants measured did not) does not act in the native transport, and a call written into its text is never read.
- **Additive fields of the external contract** (RFC 012; no schema version changes): `status` gains `backend.decision_transport` (`tool_calls` or `envelope`; `null` while unresolved), `backend.transport_reason` and `backend.parallel_tool_calls`, and `backend.structured_output` is `null` under `tool_calls`; `decision.received` gains `transport` and `text_chars` (an event recorded by 0.8 reads as `envelope`, without text).
- `mimlys-core` (RFC 012, handoff 012-2; REQ-CTX-001, REQ-CTX-003, REQ-CTX-010 amended; external design §15.4): the context of the `tool_calls` transport. The definitions travel as the request's `tools`; an earlier decision is an `assistant` message carrying its call and id, and its observation or rejection is the `tool` message answering that id, still labelled (`<<observation …>>`, `<<feedback kind="rejection">>`); the stored plan is an earlier `plan` call with the plan segment as its acknowledgement; there is no decision-request segment, so **a request never ends with an `assistant` message** (a call enters a request only with its answer). The fixed instructions of this transport keep REQ-CTX-002's three statements and say "call exactly one of the provided functions" instead of describing the envelope; the rejection hint for `malformed` says the same. The envelope transport's request, instructions included, is unchanged. The budget (LIM-C1) counts the `tools` array beside the messages; the prefix shared with the previous request is measured over the request as sent, `tools` included, in both transports. With `decision_transport = "auto"`, an engine that accepts `tools` is now asked for decisions as native calls, so the requests of a configuration written for 0.8 change shape; set `decision_transport = "envelope"` to keep 0.8's request. Whether a model returns structured calls depends on the model (the configuration chapter lists what was measured).
- `mimlys` (handoff 012, correction 1; REQ-MDL-009): in the `tool_calls` transport, `status` lists an MCP tool that the model cannot see for its function name in its server's `unavailable` (JSON and text), with the reason `function_name_invalid` or `function_name_collision`, and no longer in `tools`. A host tool is never affected: the single `run_host_tool` names it in an argument.
- `mimlys-model` (handoff 012, correction 2; LIM-M4): a configured model name without a tag matches a listed `<name>:latest`, as Ollama resolves it; 0.8 compared exactly and `status` reported a false `model_not_listed`. A name with a tag still matches only exactly.

### Documentation

- The configuration chapter: `decision_transport`, what `auto` does, which models were measured to return structured calls (spike S2: Qwen2.5-7B-Instruct 378 of 378 replies; Qwen2.5-Coder-7B and -14B none of 391) and Ollama's `num_ctx` (its OpenAI endpoint cannot set the context length and defaults to 4096 tokens; set `num_ctx` in the Modelfile). The `status` fields in the CLI reference.
- README, Getting started and the configuration chapter: "the model, plainly" now says what run B measured (release 0.9's real-model run of M4, Qwen2.5-7B-Instruct Q4_K_M: the task repaired and verified in 9 of 10 runs, 4 of 5 on llama.cpp and 5 of 5 on Ollama; one model, one task, one machine) in place of 0.8's statement that no measured model completed a task.

### Security

- Dependencies (handoff 009b; REQ-SEC-012): four advisories published after 2026-11-08 are removed by upgrade, not ignored. `rusqlite` 0.38 to 0.41 brings `libsqlite3-sys` 0.36 to 0.39 and its bundled SQLite (RUSTSEC-2026-0459; mimlys opens only a database in its owner-only data directory, so the exposure was low). `rmcp` `=3.5.0` to `=3.9.0` (RUSTSEC-2026-0457, -0461, -0462: the OAuth client, `StreamableHttpService` and the Streamable HTTP clients; none of those features is enabled, and the pin stays exact with the same features). No code changed; `SCHEMA_VERSION` stays 2, and a test opens a store written by 0.8.0 (its data in an uncheckpointed `-wal`), checks it, lists its tasks and recovers it. `Cargo.lock` moves `rusqlite`, `libsqlite3-sys`, `hashlink`, `rmcp` and, because `rmcp` 3.9 requires them, `sha2` 0.11 with `digest`, `block-buffer`, `crypto-common`, `const-oid` and `hybrid-array`; the older `sha2` stays for the other crates.

## [0.8.0] - 2026-11-08

The macOS confinement backend (M6c) completes RFC 011: 0.8.0 is M1 to M6c on Linux, Windows and macOS. The real-model run and the context limit LIM-C1 move to 0.9 (`ROADMAP.md`); under 0.8's decision format no measured local model completed a task (the M4 report, §6), and 0.9 changes how decisions are requested (RFC 012).

### Added

- `mimlys-exec`, `mimlys` (RFC 011 Amendment 2, implementation decisions, point 8; external design §13.3; LIM-O8): on macOS with an Xcode selected, the runtime makes `xcrun`'s cache file (`xcrun_db` in the per-user temporary directory) itself, outside the sandbox and with an empty environment, before it starts the first worker, by running `/usr/bin/xcrun --find <tool>` for each of `clang`, `ld`, `ar`, `ranlib`, `strip`, `libtool` and `lipo` (what a Rust link and the `cc` crate's C builds run through the `/usr/bin` shims; one named constant) and waiting at most LIM-O8 (10 s) for each (about seven seconds in all on the first start, a tenth of a second after). Without it a sandboxed `xcrun` cannot create the cache, falls back to `xcodebuild` and every build that needs the C toolchain fails on a Mac where `xcrun` never ran (measured on `macos-latest`). `check` and `status` show one line naming the file and the command to run once when the cache still cannot be made (JSON: `xcrun_cache_missing`, present only then); the run goes on. A warming that is killed or fails removes the partial file it left (a partial cache is taken for a cache and cannot be repaired from inside the sandbox); an Intel runtime on Apple silicon asks through `arch -arm64`, because the first launch of an Intel `xcrun` is translated and outlasts the wait. With the Command Line Tools selected nothing is made and nothing is shown. The profile never gets a write rule for the cache. New `LIM_O8_XCRUN_CACHE_MS`; a debug-build-only variable `MIMLYS_TEST_XCRUN` lets the tests make the warming fail.

- `mimlys-exec` (REQ-CONF-009; RFC 011 Amendment 2, implementation decisions, point 6): on macOS the worker forks a **sweeper** right after it verified its sandbox and before any thread exists: a member in a process group of its own, on `/dev/null` streams, holding the read end of a pipe whose close-on-exec write end only the worker holds. When the worker ends in any way, a crash and `SIGKILL` included, the sweeper sees end of file, kills the sandbox's other members (the tool and the processes it left behind) and exits; the worker's own loop, counts and weights exclude it. Until now a killed worker left its tools alive (confined, but able to write the workspace); Linux (cgroup) and Windows (job) already ended them. A worker that cannot start the sweeper reports K, M and C `unavailable`. A tool can kill the sweeper (members of one sandbox may signal one another); the threat register records the residual.

- `mimlys-exec`, `mimlys` (RFC 011 Amendment 2, handoff 011c; REQ-CONF-001 … 012, REQ-TEST-013): the **macOS backend** (M6c). The worker applies one Seatbelt profile to itself before its first frame, generated from the specification (canonical paths, escaped strings, `(deny default)`; `sandbox_init` resolved at run time, so a macOS without it reports `seatbelt_missing`), and every host tool inherits it. `status` reports F, N and P `enforced (seatbelt)`, E `enforced (explicit_environment)`, **K `enforced (seatbelt_membership)`** (the worker lists the pids, keeps the ones the profile lets it inspect, which are exactly the sandbox's members, and `SIGKILL`s them until none is left, after a cancel, a deadline and the tool's end: a process re-parented to `launchd` cannot escape), M `best_effort (rss_watchdog)` and C `best_effort (process_count_watchdog)` (the members' memory above LIM-H2 ends the execution `memory_limit`; their count above LIM-H3 kills the tree; polled every LIM-H6, 100 ms). The tier is `full` with **no** `accept_best_effort`. K, M and C are reported only if the worker verified, inside the applied profile, that it can list and inspect its own sandbox and neither inspect nor signal a process outside it. The read set is the measured minimum (`/usr`, `/bin`, `/sbin`, two files, the active developer directory, `xcrun`'s cache file, Rosetta's runtime where installed), one mach service (`com.apple.bsd.dirhelper`), no network, Unix sockets only under the write set, other processes' arguments and environment (`KERN_PROCARGS2`) and the process list with names refused; the dependency step's worker adds outbound TCP to port 443, name lookup through one socket and the system's certificates. A host tool can learn the numbers of the machine's processes (recorded in the threat register). New `LIM_H6_TRACK_INTERVAL_MS`. See the M6c report and "On macOS" in the host tools chapter of the book.

- `mimlys`: `mimlys toolchain revoke --all [--yes]` (Windows; REQ-CONF-008, handoff 011e): removes every permission the AppContainer holds, on mimlys's own directories and on the toolchain directories (the record's entries and, from a scan bounded to mimlys's own directories and the declared `read_paths`, the entries the record lost), then deletes the container profile and the record file, so that deleting mimlys leaves the user's directories as they were. One confirmation (`--yes` skips it), a report per entry, `--json` with `{removed, failed, profile_deleted, record_deleted}`, exit 1 with the same object if anything could not be removed (the record then holds exactly what failed). Elsewhere the command says nothing was changed outside the data directory.

### Fixed

- `mimlys`, `mimlys-core` (REQ-SBX-001, external design §12 and §18, LIM-O9, LIM-O10; handoff 005b): `mimlys interpreters install` no longer fails on one bad answer. A download is given two minutes (it had no deadline), and a transient failure (no connection, a timeout, HTTP 429 or 5xx) is retried three times after 1, 2 and 4 seconds, with one `info` line per retry; a 404 or another answer is not retried. A download that still fails is the error `unavailable` with `component: "download"` (it was `internal`, which says the runtime is at fault), naming the URL, the last status and the remedy `mimlys interpreters install <language> --from FILE`. The CI fetches the pinned interpreter once per job with retries and a cache, and installs mdbook and cargo-deny from crates.io (pinned versions, cached; the cargo-deny Docker action fetched its binary with an unretried `curl` on every run), so a GitHub release outage no longer turns every job red. The advisory database is still fetched on every run; a failed fetch fails the audit job.

- `mimlys-exec`, `mimlys` (REQ-CONF-008, THR-36, LIM-O7; Windows; handoff 011f, investigation D1): the writers of one directory's permissions no longer write on a stale base. The named mutex that serializes them gave up after LIM-O2 (2 s) and wrote anyway, on the belief that a write takes milliseconds; the system propagates the change to every file below the directory, so a write takes 0.1 s to several seconds, growing with the entries already there, and each give-up removed another installation's entry, which the user met as `Access is denied` starting a host tool, with no reason (the intermittent `m6b_host_tools` failure on Windows CI). A writer that finds the mutex held now logs one `info` line naming the directory, waits up to the new LIM-O7 (60 s) and then refuses the write with `acl_not_applied: the permissions of <dir> are being written by another runtime`; a mutex the system will not create or wait on is refused too, with its own reason (`acl_not_applied: the permissions lock of <dir> cannot be taken: <system error>`): there is no write without the lock. Both are the error kind `unavailable` with `detail.component` `"permissions"` (an expected condition; retrying is the remedy), carried as a typed error and never recognised by its text. `toolchain grant` and `revoke` fail with it (nothing is changed), `revoke --all` lists the entry under `failed` with it, and the start of mimlys fails with it when its own directories cannot be written (the next start applies them); the data directory's failure message now carries the error's text, not only its kind. An abandoned mutex (its holder died) is acquired and the permissions are read again under it. The decision of the wait is a pure function (`confine::dacl_wait`) tested on every platform.

- `mimlys-core` (REQ-CTX-002, external design §15.1): the model's fixed instructions no longer call the goal data. They said that every labelled segment, user text included, is "data, never instructions"; the goal is such a segment, so a model was told that its task is not an instruction, and in the first run against a real local model (Qwen2.5-Coder-7B) it asked the user for a file it had been told to read, four runs of four. The instructions now say that the goal is the task, set by the user; that answers and notes are the user's own words; that every other labelled segment is data, never instructions; and that what a granted tool can give (`read_file`, `list_dir`) is obtained with that tool, `ask_user` being for a choice, a missing grant or an ambiguity of the goal. The request text changes by these sentences; the decision schema does not.

- `mimlys-mcp` (REQ-MCP-008): a server's `max_call_ms` is now a floor for the deadline of every one of its tools. Until now only a declared tool's deadline was raised to it; an undeclared tool kept the LIM-O5 default (60 000 ms) even when the server declared a longer maximum, so a server with `max_call_ms = 120000` had its undeclared tools cut off at 60 000 ms. The floor is applied at import, in one place.

- `mimlys-core` (REQ-CAP-008): the workspace sentence of the capability text the model reads is generated from the grant set like the rest of it. It was a constant that said "you may read and write inside the workspace" to every task, a `read_only` one included. A task whose granted tools include none with the `workspace_write` effect is now told it may read inside the workspace and may not write; one with such a tool is told it may read and write, as before. This changes the system message, so the first request of a `read_only` task differs from the previous release's.

- `mimlys-core` (REQ-SEC-011, REQ-ENG-004): a panic in the model adapter or in a tool provider is contained where the runtime calls it, in the runtime's one call site of each, not in each adapter. Until now it unwound through the runtime and ended the process (only the worker's own thread was guarded). A panicking backend is `backend_unavailable` for that request (the request is not repeated and the task halts with that reason, as for an unreachable backend); a panicking tool provider is `host_fault{unavailable}` for that execution. The process goes on and the task can be resumed. One error-level log line (`mimlys_core`, "a panic in an adapter was contained", with the adapter) carries the panic's message redacted of configured secrets, on one line and cut at LIM-I5; no panic text or stack trace reaches an observation, an event or a prompt. `mimlys-core` gains the `tracing` facade as a dependency (no I/O).

- `mimlys-core`, `mimlys-exec`, `mimlys` (REQ-SEC-011, REQ-ENG-004): the containment of a panic in an adapter is complete. Every call the runtime makes into a model backend (`describe`, `locality`, `generate`, `last_usage`) or a tool provider (`definitions`, `imports`, `refresh_pins`, `drain_events`, `execute`) is contained: a panic at task creation or in the status is `unavailable` for that component (no task exists yet; none is left half-created); at a step it halts the task `tool_unavailable` with its state change recorded, like a failed `execute`; one in `last_usage` loses the usage figure and the step goes on. The events of `drain_events` are audit records, so a panic there is treated like the other provider calls. A call dropped while it is still running (its task cancelled) drops the adapter's future under containment too. `mimlys` and `mimlys-worker` install a panic hook first thing in `main`: a panic that ends a thread writes one JSON line to standard error, with the crate-relative `location` of the panic (`src/runtime/loop_.rs:412`, never the absolute path), redacted of the configured secrets (once the configuration has loaded), on one line and cut at LIM-I5, instead of Rust's default text with its location; a panic the runtime contains and logs itself is not written twice. Panics in the persistence and the workspace adapter are not contained, by design: the process ends and the next start recovers.

- `mimlys`, `mimlys-exec` (REQ-WS-001, THR-31): the data directory is owner-only from the start. On Unix the data directory, the parents the runtime creates for it and `workspaces/`, `tmp/` and `interpreters/` are created with mode 0700 (given to `mkdir`; before, the data directory was created with the umask's mode, normally 0755, and tightened by the store a moment later, and the three subdirectories stayed 0755 under the 0700 root); an existing directory with another mode is brought to 0700 at every start. On Windows the data directory now gets a protected DACL granting the current user full control and nobody else, inherited by what is created beneath, at every start and before the AppContainer's entries are added to the subdirectories (until now it had whatever its parent's DACL inherited; the default location under the user's profile was private by that, a configured one need not have been). The system and administrator accounts therefore have no entry in it; the owner can always change the DACL. The call is a new function in `crates/mimlys-exec/src/confine/windows/acl.rs`.

### Changed

- **Error kinds (external design §18): two refusals are `unavailable`, no longer `internal`.** `detail.component` is `"permissions"` when, on Windows, the permissions of a directory cannot be written because another runtime is writing them past LIM-O7 or their lock cannot be taken (retry later), and `"download"` (with `url` and `last_status`) when an interpreter download still fails after its retries; the message of the second names `mimlys interpreters install <language> --from FILE`. A client that matched `internal` for these must match `unavailable` and the component (see the Fixed entries on the permission lock and the download).
- **JSON output:** `check` and `status` gain `data_dir_in_temporary_directory` (all platforms) and, on macOS, `xcrun_cache_missing` (the path of `xcrun`'s cache when the runtime could not make it, else null).
- **Standard error after a panic:** `mimlys` and `mimlys-worker` replace Rust's default panic text (the message and its location, unredacted) with one JSON line carrying the crate-relative location and the message, redacted of the configured secrets and cut at LIM-I5. A script that parsed the default text must read the line instead.
- **The model's instructions (REQ-CTX-002):** the fixed instructions in every decision request now say that the goal is the task (they had called it data) and that a granted tool is used before `ask_user`. The decision schema is unchanged. A model's behaviour may differ from 0.7.1; no measured local model completes the task under 0.8's decision format (the M4 report, §6).

- `mimlys-core`, `mimlys-exec` (REQ-SBX-003, external design §7.4, §7.5): a new termination, **`process_limit`** (snake_case, as every other), mapped to `resource_exhausted{processes}` with the disposition of the other resource limits (feedback). The macOS count watchdog ends a tree that grows past LIM-H3 with it; until now such a tree was reported as a tool that exited with status 137, which told the model nothing. Where the kernel refuses the extra process (Linux, Windows) nothing changes: the tool sees a failed `fork` and its own ending is reported. An observation, an event or a control-API client that enumerates terminations gains a value; the termination list in the external design and the requirements already names it.

- `mimlys` (REQ-CONF-011, external design §13.5): a host tool's `command` whose canonical target, after its links, leaves the read paths (the declared ones, the data directory's `interpreters` and `tmp`, the worker's directory and the system's) is refused when the configuration loads, on every platform, naming the declaration, the resolved path and the directory to declare in `read_paths`. Homebrew's `rustup` links `cargo` into `/opt/homebrew/Cellar/…`, which a confinement matches; before, the tool failed later with a bare permission error. A command that cannot be resolved here is still not refused at load (the run says so).

## [0.7.1] - 2026-11-04

Release 0.7.1 is the hardening of the Linux backend that the intake review
after 0.7.0 asked for (RFC 011 Amendment 1, handoff 011d). 0.7.0 is tagged and
not published; 0.7.1 is the first release on crates.io.

### Security

- `mimlys-exec` (Linux, REQ-CONF-012): clause N could be defeated by project
  code running in a host tool. A socket created through `io_uring`
  (`IORING_OP_SOCKET`, Linux 5.19 and later) never passes the `socket` rule of
  the seccomp filter, so the filter now always denies `io_uring_setup`,
  `io_uring_enter` and `io_uring_register` (in the dependency step's worker
  too) together with `process_vm_readv` and `process_vm_writev` (another
  process's memory, which the denial of `ptrace` did not cover). Where
  Landlock's ABI is 4 or later (Linux 6.7) and network is denied, the ruleset
  also handles TCP `bind` and `connect` with no rule, a second layer under the
  filter; `status` then reads `enforced (seccomp+landlock_net)` for clause N,
  `enforced (seccomp)` on an older kernel.
- `mimlys`, `mimlys-exec` (REQ-CONF-012): the runtime and the worker mark
  themselves non-dumpable first thing, so another program of the same user
  cannot read their memory, environment or descriptors through `/proc`
  (`env:`-referenced secrets sit in the runtime's environment). Cost: no core
  dump of either, and no `ptrace` of either as the same user.
- `mimlys-exec` (Linux, REQ-CONF-011): the processes of the machine left the
  read set. `/proc` is no longer readable by a host tool: its command lines
  and network tables stay out of project code. The worker keeps `/proc` for its
  own descendant walk (clause K on the `subreaper` rung); a host tool's process
  restricts itself to the same sets without it before it runs, as a second
  Landlock layer. (Landlock's ptrace scoping already refused another process's
  `environ`, `maps` and `fd`; the read set was where `cmdline` and the rest
  leaked.)
- `mimlys-core`, `mimlys` (REQ-CONF-011, LIM-H5): a declared read path may not
  expose credentials. A filesystem root, the home directory, an ancestor of it,
  or a directory that directly holds a name of LIM-H5 or LIM-W5 (`~/.cargo`
  holds `credentials.toml`) is refused when the configuration loads and by
  `toolchain grant`, naming the entry found and the narrower path to declare.

- Event vocabulary (external design §17.1): `execution.finished{attempt, termination}` is the event of persistence line 6 (one per execution, from the tool actor); `action.finished{status, cause?}` is emitted once, at line 7. Metrics no longer count an action twice (handoff 010).
- Approvals (external design §10.2): a grant issued or an unrelated grant revoked while an approval is pending withdraws the request and asks again under the new grant set, so the user is never asked to approve under grants that no longer apply; revoking a grant the action uses rejects it `denied` (handoff 010).
- Task state machine: a resume that would halt again at once (deadline passed, step budget used up) is refused with a message naming the extension to give; `task.pause_requested` is recorded as an event (handoff 010).
- Validator SPI: the budget-reservation hook receives the canonical arguments, so a write larger than the remaining workspace quota is refused before execution (handoff 003).
- External design §8: notice `entries_skipped{reason, count}` added for listings and searches; §11: `write_file` creates missing parents and reports `parents_created`, `list_dir` lists symbolic links as type `symlink`, `read_file` fails with `line_out_of_range` past the end, `search_files` reports skipped entries and per-match truncation; §6.3 stage 7 names absolute paths explicitly.
- External design §7.1: an action that is `proposed`, `waiting_approval` or `authorized` is also cancelled when its task is cancelled.
